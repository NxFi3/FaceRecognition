# راهنمای سادهٔ NxFi: اجرای برنامه و فهم بخش تجاری

این متن راهنمای کاربری و توسعه است؛ نام برند در رابط کاربری «NxFi» است و محصول فعلی FaceRecognition نام دارد. نام تجاری به معنی ثبت حقوقی شرکت، گواهی امنیتی یا اثبات آمادگی فروش نیست.

## اول فرق دو بخش را بدانیم

**برنامهٔ دسکتاپ مدرسه** روی کامپیوتر مدرسه اجرا می‌شود. این برنامه دوربین را می‌خواند، تشخیص و رهگیری را انجام می‌دهد، حضور و غیاب را در پایگاه دادهٔ محلی ثبت می‌کند و گزارش می‌سازد. تصاویر و اطلاعات زیستی برای «تشخیص ابری» به سرور فرستاده نمی‌شوند؛ این پروژه سرویس تشخیص ابری ندارد.

**سرویس کنترل و سایت تجاری** یک برنامهٔ وب Django جداگانه است. مسئول حساب‌های مدرسه، اشتراک و تاریخ انقضا، مجوز نصب، سفارش و پرداخت دستی، فایل‌های انتشار، تیکت‌ها و مدیریت مالک است. این سرویس تصمیم نمی‌گیرد که یک چهره در تصویر به کدام دانش‌آموز تعلق دارد؛ آن کار در دسکتاپ انجام می‌شود.

برای همین اجرای `python src/app.py` به‌تنهایی سایت و سرویس کنترل را راه‌اندازی نمی‌کند. دسکتاپِ سورس به تنظیمات عمومی سرویس HTTPS معتبر نیاز دارد. برای تست محلیِ هر دو بخش از پایلوت محلی استفاده کنید.

## اجرای آزمایشی روی کامپیوتر خودت

در ریشهٔ مخزن و در محیط Conda پروژه:

```bash
conda activate AI
python -m pip install -r requirements.txt
python -m pip install -r requirements-service.txt
python -m tools.run_local_pilot
```

این فرمان دادهٔ مصنوعی، پایگاه دادهٔ جدا، کلید امضای موقت و گواهی TLS برای localhost می‌سازد. سرویس فقط روی loopback گوش می‌دهد و سپس برنامهٔ دسکتاپ را باز می‌کند. با بستن دسکتاپ، سرویس آزمایشی هم بسته می‌شود.

آدرس‌ها و مسیر فایل رمزهای آزمایشی در ترمینال چاپ می‌شوند. معمولاً:

- پنل مالک: `https://localhost:18443/owner/`
- ورود مدرسه/کاربر: `https://localhost:18443/login/`
- حساب‌های مصنوعی: `~/.local/share/nxfi-facerecognition-pilot/pilot-test-accounts.txt`

برای اجرای فقط سایت و سرویس در ترمینال:

```bash
python -m tools.run_local_pilot --server-only
```

برای ساخت یک محیط تست جداگانه (مثلاً اگر قبلاً مسیر مدل‌ها از مخزن قدیمی باقی مانده):

```bash
python -m tools.run_local_pilot --data-dir ~/.local/share/nxfi-facerecognition-pilot-review
```

در این حالت هم فایل رمزهای آزمایشی در همان پوشهٔ انتخابی ذخیره می‌شود. این حساب‌ها فقط برای تست هستند؛ هیچ‌وقت آن‌ها را برای مشتری واقعی یا برای دادهٔ واقعی مدرسه استفاده نکن. بررسی TLS را با `verify=False` یا غیرفعال‌کردن اعتبارسنجی گواهی دور نزن. هشدار گواهی مرورگر باید با اعتماد درست به گواهی محلی حل شود.

## گردش‌کار تجاری از ابتدا تا انتها

### ۱. اپراتور سرویس را راه می‌اندازد

برای سرویس عمومی، اپراتور به دامنه و DNS درست، یک میزبان Ubuntu پشتیبانی‌شده، Docker Compose، HTTPS عمومی، SMTP واقعی و نسخهٔ بازیابی امن از secrets نیاز دارد. فرمان `python -m deploy.configure` فایل `deploy/.env` حاوی رازهای خصوصی و `deploy/generated/subscription-client.json` حاوی فقط آدرس سرویس و کلید عمومی را می‌سازد. این فرمان **سایت را اجرا یا روی اینترنت منتشر نمی‌کند**.

`deploy/.env` و کلیدهای امضا/بازیابی بسیار محرمانه‌اند. آن‌ها را در Git، تیکت، اسکرین‌شات یا فایل قابل دانلود مشتری قرار نده. اگر قبلاً یک فایل `.env` واقعی ساخته‌ای، دوباره کلیدها را تولید نکن؛ ممکن است بکاپ‌های قبلی به آن کلیدها وابسته باشند.

پس از تنظیم SMTP و مقادیر واقعی کسب‌وکار، Compose سرویس وب، PostgreSQL، Redis و پراکسی HTTPS را بالا می‌آورد. قبل از استفادهٔ عمومی، DNS، گواهی، تحویل ایمیل، بکاپ خارج از سرور و بازیابی سرد باید واقعاً آزمایش شوند.

### ۲. مالک طرح و نسخه را آماده می‌کند

مالک شرکت وارد `/owner/` می‌شود. مالک باید با دستور provision مالک ایجاد شود؛ صرفاً Django staff/superuser بودن مجوز مالکیت تجاری نمی‌دهد.

مالک از پنل طرح را با قیمت و واحد صحیح، مدت اشتراک، سقف دانش‌آموز و تعداد دستگاه تعریف و منتشر می‌کند. قیمت‌های نمونه یا draft به معنی عرضهٔ واقعی نیستند. فایل نصب نیز خودکار اختراع یا ساخته نمی‌شود: اپراتور باید یک فایل انتشار تأییدشده، دارای hash، را در محل release میزبان نصب کند و سپس نسخه و فایل را از پنل منتشر کند.

### ۳. مدرسه حساب می‌سازد و سفارش ثبت می‌کند

مدرسه در سایت ثبت‌نام و ایمیلش را تأیید می‌کند، وارد حساب می‌شود، طرح منتشرشده را انتخاب می‌کند و سفارش ایجاد می‌کند. مبلغ سفارش را سرور از طرح ثبت‌شده حساب می‌کند؛ نباید به مبلغ ارسالی از مرورگر اعتماد شود.

در نسخهٔ فعلی **درگاه پرداخت ایرانی وصل نشده است**. مدرسه می‌تواند رسید یا شناسهٔ پرداخت را برای بررسی ثبت کند، اما این کار به‌تنهایی نه پرداخت را تأیید می‌کند و نه اشتراک را فعال می‌سازد.

### ۴. مالک پرداخت را مستقل بررسی و تأیید می‌کند

مالک باید واریز را در حساب یا سامانهٔ مالی واقعی خود بررسی کند و فقط در صورت درست بودن مبلغ و سفارش، از پنل پرداخت را تأیید کند. تأیید معتبر توسط مالک باعث ثبت پرداخت و ساخت/تمدید حق اشتراک در سرور می‌شود. رد رسید یا مبلغ اشتباه نباید مجوز فعال بسازد. رسید ارسالی مدرسه به‌خودی‌خود مدرک بانکی قطعی نیست.

بنابراین سایت فرایند تجاری ثبت سفارش و بررسی پرداخت را مدیریت می‌کند؛ **پول را خودش دریافت نمی‌کند** و هنوز تأیید خودکار از درگاه بانکی ندارد.

### ۵. مدرسه برنامهٔ دسکتاپ را فعال می‌کند

بستهٔ رسمی ویندوز باید هنگام ساخت با فایل عمومی `subscription-client.json` تنظیم شده باشد. این فایل شامل URL HTTPS سرویس و کلید عمومی Ed25519 برای اعتبارسنجی مجوز است؛ نباید کلید خصوصی سرور داخل بسته قرار بگیرد.

مدرسه با حسابش از داخل دسکتاپ وارد می‌شود. سرویس مجوز امضاشده را برای مدرسه، نصب و حدود مجاز صادر می‌کند. کلاینت امضای آن را بررسی می‌کند، دستگاه را به مدرسه متصل می‌کند و پس از فعال‌سازی، مجوز معتبر می‌تواند تا پایان اعتبارش به‌صورت آفلاین کار کند. همگام‌سازی شبکه در پس‌زمینه انجام می‌شود. به همین دلیل نصب کاملاً آفلاین را نمی‌توان فوراً از راه دور لغو کرد؛ وضعیت لغو پس از همگام‌سازی به نصب می‌رسد.

### ۶. حضور و غیاب و بکاپ

بعد از فعال‌سازی، تشخیص چهره، رهگیری و ثبت حضور در دسکتاپ و روی دستگاه مدرسه انجام می‌شود. سرور قرار نیست ویدئوی زنده یا استنتاج مدل را میزبانی کند.

پشتیبان‌گیری کامل آنلاین اختیاری است و بستهٔ دادهٔ مدرسه از سمت کلاینت رمزگذاری می‌شود. کلید بازیابی مدرسه باید جدا از بکاپ و به‌صورت امن نگهداری شود. اگر مدرسه تمام نسخه‌های کلید را گم کند، فروشنده به‌طور خودکار نمی‌تواند بکاپ رمزگذاری‌شده را باز کند. مالک سرویس ابزارها و وضعیت مدیریت بکاپ را می‌بیند؛ این به معنی دسترسی عادی به عکس‌های خام مدرسه نیست.

## پنل مالک برای چیست؟

پنل `/owner/` برای مدیریت خود پلتفرم است، نه برای ثبت حضور روزانهٔ دانش‌آموزان. بر اساس قابلیت‌های پیاده‌سازی‌شده، بخش تجاری این موارد را پوشش می‌دهد:

- حساب مدارس و وضعیت اشتراک/ظرفیت/دستگاه‌ها
- طرح‌ها و سفارش‌های تجاری
- بررسی پرداخت دستی، صورتحساب و سابقهٔ عملیات
- انتشار نسخه‌های واقعی دانلود و اطلاعات فایل
- تیکت پشتیبانی، درخواست تماس و عملیات سلامت سرویس
- عملیات بکاپ و سوابق حسابرسی مدیریتی

دسترسی مالک باید با حساب مجاز و احراز هویت مجدد برای عملیات حساس باشد. حساب عادی مدرسه نباید به اطلاعات و عملیات مدرسهٔ دیگر یا پنل مالک دسترسی داشته باشد. این دسترسی‌ها را باید با دو حساب آزمایشی مستقل و تست‌های منفی بررسی کرد.

## کدام قابلیت‌ها هنوز برای فروش واقعی آماده نیستند؟

داشتن صفحات و کد تجاری به معنی تأیید عملی انتشار نیست. پیش از مشتری واقعی هنوز باید با زیرساخت حقیقی بررسی شوند: ساخت و نصب نسخهٔ ویندوز، Qt/DLLها و مدل‌ها، فعال‌سازی و انقضای مجوز، خواب/راه‌اندازی مجدد، دو دوربین واقعی، کیفیت تشخیص و نرخ خطا روی سخت‌افزار هدف، SMTP واقعی، DNS/HTTPS، خروجی و بازیابی بکاپ خارج از سرور، و آزمون امنیتی مستقل. درگاه پرداخت ایرانی و تشخیص ابری نیز قابلیت‌های عرضه‌شدهٔ این نسخه نیستند.

## چند فرمان که نباید با هم اشتباه شوند

- `python -m tools.run_local_pilot`: تست یکپارچهٔ دسکتاپ + سرویس محلی با دادهٔ مصنوعی.
- `python -m tools.run_local_pilot --server-only`: فقط سایت/سرویس پایلوت؛ ترمینال باید باز بماند.
- `python -m deploy.configure --domain ... --email ...`: ساخت تنظیمات برای استقرار سرور عمومی؛ این فرمان سرور را اجرا نمی‌کند.
- `docker compose ... up -d --build`: اجرای استقرار Compose پس از تنظیم و بازبینی واقعی متغیرهای میزبان؛ روی کامپیوتر توسعه به‌طور خودکار جایگزین پایلوت محلی نیست.
- `python -m unittest discover -s tests -v`: تست‌های مستقل پایتون؛ این‌ها جای تست واقعی دوربین و نصب ویندوز را نمی‌گیرند.

قاعدهٔ ساده: ابتدا پایلوت محلی را با دادهٔ مصنوعی اجرا کن، گردش‌کار مالک و مدرسه را بفهم، بعد سراغ استقرار عمومی برو. هرگز secrets یا دادهٔ واقعی مدرسه را برای حل خطای آزمایشی حذف یا کپی نکن.
