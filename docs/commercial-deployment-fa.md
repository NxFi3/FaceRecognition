# راه‌اندازی پلتفرم تجاری NxFi

نام NxFi در این پروژه موقت است؛ این راهنما ثبت حقوقی شرکت،
مجوز پردازش دادهٔ دانش‌آموز یا اتصال درگاه پرداخت را تأیید نمی‌کند.
این شاخه روی `hardening/offline-first-licensing@bb75a65` بنا شده و کد تشخیص
و تصمیم حضور و غیاب را برای فروشگاه بازنویسی نمی‌کند. راهنمای کامل مجوز
آفلاین، کلید بازیابی و بازیابی ویندوز در
[subscription-setup-fa.md](subscription-setup-fa.md) باقی است.

## ساختار شرکت و محصول

صفحهٔ `/` معرف NxFi است و `/products/` کاتالوگ محصولات عرضه‌شده.
مسیر کامل FaceRecognition از `/products/facerecognition/` آغاز می‌شود؛ قیمت،
دانلود و پرتال اختصاصی آن زیر همین مسیرند. `/account/` ورودی حساب شرکت و
`/owner/` پنل مشترک مالک است. فعلاً فقط FaceRecognition محصول تجاری قابل سفارش
است؛ ثبت یک ردیف Product دیگر، آن را عرضه یا قابل پرداخت نمی‌کند.

مهاجرت `0005` محصول فعلی را ایجاد و طرح/سفارش/فایل/تیکت‌های قبلی را به آن
متصل می‌کند؛ تاریخ، ظرفیت، دستگاه و مجوز قبلی تغییر نمی‌کنند. قبل از مهاجرت
بکاپ بگیرید. کلیدهای امضا و master backup را دوباره تولید نکنید. جزئیات در
[معماری شرکت و محصول](corporate-product-architecture.md) آمده است.

## اجرای محلی فقط با اطلاعات مصنوعی

برای توسعهٔ رابط وب بدون VPS و HTTPS عمومی، وابستگی‌های سرویس و پروفایل
صریح لوکال را استفاده کنید. این پروفایل تنها برای loopback است، ایمیل را
در console چاپ می‌کند و کلید تولیدیِ امضای مجوز ندارد. هرگز دیتای واقعی
مدرسه یا رمز واقعی را در آن وارد نکنید و آن را روی `0.0.0.0` منتشر نکنید.
متغیرهای `DATABASE_URL` و `SERVICE_TEST_DATABASE_URL` نباید تنظیم باشند؛ این
کنترل جلوی استفادهٔ تصادفی از دیتابیس تولیدی را می‌گیرد.

```sh
python -m pip install -r requirements-service.txt
export NXFI_LOCAL_DEVELOPMENT=1
export DJANGO_SETTINGS_MODULE=service.dev_settings
python -m service.manage migrate
python -m service.manage provision_owner --email owner@example.invalid
python -m service.manage runserver 127.0.0.1:8000
```

وب در `http://127.0.0.1:8000/` است. دیتابیس مصنوعی پیش‌فرض
`data/commercial-dev.db` است؛ برای محیط آزمایشی جدا، `NXFI_DEV_DATABASE` را
به مسیر تازه بدهید. آدرس‌های تأیید ایمیل فقط برای همین دادهٔ ساختگی در
console دیده می‌شوند. برای آزمون مستقل مجوز واقعی از
`SERVICE_TESTING=1 python -m tools.smoke_offline_license` در shell جدا و بدون
پروفایل dev استفاده کنید. برای فعال‌سازی دسکتاپ واقعی، staging HTTPS با
کلیدهای پایدار و امن لازم است.

## استقرار اولیهٔ سرور

برای استقرار عمومی هنوز دامنه، VPS، سرویس SMTP و مسئول نگهداری لازم دارید؛
این تغییرات هیچ زیرساختی نمی‌خرند و خودکار روی اینترنت منتشر نمی‌شوند.
روی میزبان تازهٔ Ubuntu 24.04، Docker Compose را مطابق راهنمای اشتراک آماده
کنید و نسخهٔ بازبینی‌شدهٔ همین شاخه را دریافت کنید. سپس:

```sh
python -m pip install -r requirements-cloud.txt
python -m deploy.configure --domain schools.your-domain.ir --email owner@your-domain.ir
```

`deploy/environment.example` فقط فهرست متغیرها و توضیح آن‌هاست؛ مقدارهای نمونهٔ
آن برای اجرا معتبر نیستند. generator فایل واقعی `deploy/.env` با دسترسی
`0600` و کلیدهای تصادفی می‌سازد و از بازنویسی فایل موجود خودداری می‌کند.
`.env` و نسخهٔ بازیابی آن محرمانه‌اند؛ تنها
`deploy/generated/subscription-client.json` عمومی و قابل تحویل به دسکتاپ است.

در `.env` مقادیر SMTP و فرستندهٔ تأییدشده را وارد کنید. برای پرداخت دستی،
`MANUAL_PAYMENT_INSTRUCTIONS` را با دستور پرداخت واقعی و تأییدشدهٔ کسب‌وکار
پر کنید. اگر خالی باشد، سایت باید مشتری را برای هماهنگی پرداخت به پشتیبانی
هدایت کند؛ شمارهٔ حساب یا پرداخت موفق اختراع نمی‌شود. نام دریافت‌کننده، واحد مبلغ و مسیر ارسال شناسهٔ واریز را روشن
بنویسید؛ اطلاعات حساب اشخاص یا پرداخت آزمایشی را به‌عنوان درگاه واقعی معرفی
نکنید. برای متن دارای فاصله، `#` یا `$` از قواعد نقل‌قول dotenv در Compose
استفاده کنید. `CONTACT_RESPONSE_DAYS` زمان هدف پاسخ‌گویی نمایش‌داده‌شده است؛
تعهد تجاری واقعی را مطابق ظرفیت تیم خود تعیین کنید.

```sh
sudo docker compose --env-file deploy/.env -f deploy/compose.yml config --quiet
sudo docker compose --env-file deploy/.env -f deploy/compose.yml up -d --build
sudo docker compose --env-file deploy/.env -f deploy/compose.yml ps
```

فقط ۸۰ و ۴۴۳ برای Caddy عمومی‌اند. Gunicorn، PostgreSQL و Redis را جداگانه
منتشر نکنید. پنل وب با UID غیرریشه، فایل‌سیستم فقط‌خواندنی و tmpfs محدود
اجرا می‌شود. تنظیمات proxy و Host را با همان topology نگه دارید؛ اعتماد به
`X-Forwarded-*` روی Gunicorn منتشرشده امن نیست. DNS و گواهی HTTPS واقعی و
تحویل SMTP باید روی زیرساخت واقعی شما جداگانه آزمایش شوند.

## ایجاد حساب انحصاری مالک

مالک شرکت از روی `staff`، `superuser`، نام کاربری خاص یا رمز داخل مخزن تعیین
نمی‌شود. پس از migration، از کنسول مورد اعتماد سرور اجرا کنید:

```sh
sudo docker compose --env-file deploy/.env -f deploy/compose.yml exec web python -m service.manage provision_owner --email owner@your-domain.ir
```

برای حساب جدید، رمز و تکرار آن به‌صورت تعاملی دریافت می‌شود؛ برای حساب
موجود تأیید رمز همان حساب لازم است. رمز را در آرگومان command،
متغیر محیطی عمومی، screenshot یا Git نگذارید. حساب مدرسه نباید به مالک تبدیل
شود. برای انتقال مالکیت، دستور `--replace` تنها با تأیید رمز مالک فعلی
استفاده می‌شود؛ قبل از اجرا نسخهٔ بازیابی سرور بگیرید. در پنل عملیات حساس
به بررسی مجدد رمز در بازهٔ کوتاه نیاز دارد؛ داشتن session قدیمی کافی نیست.
حساب‌های قبلی مدرسه حفظ می‌شوند ولی staff یا superuser بودن به‌تنهایی اجازهٔ
پنل مالک یا Django admin را نمی‌دهد. دستور قدیمی `createsuperuser` جایگزین
provisioning مالک نیست.

## طرح، سفارش و پرداخت دستی

برای پیش‌نویس‌های غیرفعال می‌توانید فرمان `seed_plans` را اجرا کنید؛ این
فرمان هیچ قیمت فعال یا اشتراکی ایجاد نمی‌کند. سپس از پنل مالک، طرح‌های واقعی را با قیمت صحیح، واحد پول، مدت، ظرفیت و
تعداد دستگاه ثبت و منتشر کنید. قیمت‌ها را در فرانت‌اند hardcode نکنید.
طرح آزمایشی/درخواست دمو را از اشتراک پرداخت‌شده متمایز نگه دارید؛ نام آن‌ها
نباید به مشتری القا کند که محصول پردازش ابری موجود یا فعال است.

مدرسه پس از ثبت‌نام و تأیید ایمیل، طرح را از سایت انتخاب و سفارش خود را
ایجاد می‌کند. مبلغ و حدود سفارش از دادهٔ سرور گرفته می‌شوند، نه ورودی مبلغ
مرورگر. ثبت شناسهٔ واریز فقط درخواست بررسی است و اشتراک را فعال نمی‌کند.
مالک باید واریز را در منبع بانکی/مالی واقعی خود بررسی کند؛ سپس در پنل با
reauthentication آن را تأیید کند. تأیید موفق و معتبر، پرداخت ثبت‌شده و
استحقاق اشتراک را در یک تراکنش تکمیل می‌کند. کلیک دوباره نباید تمدید را
دوبار اعمال کند. برای درخواست ردشده یا پرداخت ناموفق هیچ فعال‌سازی انجام
نمی‌شود. صورتحساب پلتفرم، خودبه‌خود صورتحساب رسمی مالیاتی ایران نیست؛ وضعیت
حقوقی/مالیاتی و اطلاعات فروشنده را پیش از فروش واقعی بررسی کنید.

اتصال درگاه ایرانی در این نسخه انجام نشده است. provider آینده باید مبلغ،
پذیرنده، شناسهٔ سفارش و وضعیت تراکنش را مستقیماً از سرویس معتبر درگاه
تأیید کند؛ redirect مرورگر یا payload ادعایی مدرسه دلیل پرداخت نیست. تا
داشتن حساب پذیرندگی، قرارداد درگاه و آزمون sandbox/واقعی لازم، آن را در
وب‌سایت به‌عنوان پرداخت آنلاین فعال معرفی نکنید.

تمدید از مسیر سفارش/پرداخت معتبر انجام می‌شود؛ برای ارتقا، لغو یا تغییر
ظرفیت از درخواست ثبت‌شده و بررسی مالک استفاده کنید. کاهش ظرفیت نباید دادهٔ
قدیمی را پاک کند. تغییر اشتراک در سرور پس از اتصال بعدی به مجوز امضاشدهٔ
دسکتاپ منتقل می‌شود. مجوز معتبر آفلاین با قطعی سرور باطل نمی‌شود؛ لغو
آنی نصب کاملاً آفلاین ممکن نیست.

## انتشار فایل قابل دانلود

وب‌سرویس نباید فایل EXE دلخواهِ آپلودشده از مرورگر را منتشر کند. artifacts
تأییدشده را اپراتور در `deploy/releases/` میزبان قرار می‌دهد؛ Compose این
پوشه را فقط‌خواندنی در `/data/releases` می‌بیند. نام‌ها باید نام فایل ساده
باشند؛ از symlink یا مسیر بیرون این پوشه استفاده نکنید. فایل خصوصی، کلید
امضا، `.env` یا کلید مدرسه را هرگز در این پوشه نگذارید.

قبل از انتشار، Windows x64 build و smoke test، Qt/DLL و مدل‌های ONNX/dlib
را روی میزبان واقعی بررسی کنید. اگر مبنای پایلوت OSNet دارد، همان وزن‌ها و
وابستگی‌های CPU را با `FACE_REID_CACHE` بسته‌بندی کنید؛ حذف خاموش آن کیفیت
پایلوت را حفظ نمی‌کند. hash manifest و نسخهٔ وابستگی‌ها، commit سازنده و
نتیجهٔ آزمون را نگه دارید. EXE را با گواهی معتبر خود امضا و رفتار آنتی‌ویروس
را بررسی کنید؛ در این محیط لینوکس نتیجهٔ ساخت ویندوز ادعا نمی‌شود.

پس از کپی فایل نهایی و تنظیم مجوز خواندن UID سرویس، metadata نسخه، اندازه و
SHA-256 را از پنل مالک ثبت/منتشر کنید. در سایت تنها release واقعاً موجود
و مجاز نمایش داده شود. حذف انتشار، مجوز دانلود جدید را قطع می‌کند ولی
نصب‌های قبلی را خودبه‌خود حذف نمی‌کند. payloadهای انتشار را جدا از بکاپ
مدارس نگه دارید و یک نسخهٔ قابل بازتولید از هر release حفظ کنید.

## ایمیل، پایش و نگهداری

اعلان تجاری در outbox پایدار ثبت می‌شود تا شکست SMTP، پرداخت یا تمدید
موفق را برنگرداند. اجرای دوره‌ایِ محدود به پیام‌های آماده را در cron یا
سامانهٔ job خود قرار دهید:

```sh
sudo docker compose --env-file deploy/.env -f deploy/compose.yml exec -T web python -m service.manage flush_commercial_emails
```

پارامترها و وضعیت outbox را در help دستور و پنل بررسی کنید؛ delivery ایمیل
با صرفِ ایجاد رکورد اثبات نمی‌شود. SPF/DKIM/DMARC، خطای SMTP و صف باقی‌مانده
را پایش کنید. برای retry بی‌نهایت یا ارسال چندبارهٔ دائمی برنامه‌ریزی نکنید.

دستورهای پایهٔ بررسی:

```sh
sudo docker compose --env-file deploy/.env -f deploy/compose.yml exec web python -m service.manage check --deploy --fail-level WARNING
sudo docker compose --env-file deploy/.env -f deploy/compose.yml logs --tail 100 web
sudo docker compose --env-file deploy/.env -f deploy/compose.yml exec web python -m service.manage prune_backup_orphans
```

دستور prune پیش‌فرض dry-run است. فقط پس از بررسی، `--apply` فایل بدون رکورد
و قدیمی‌تر از مهلت امن را حذف می‌کند. سلامت DB/Redis، فضای دیسک و tmpfs،
quota مدارس، خطاهای دانلود، سفارش‌های معلق، گواهی و بکاپ بیرون VPS را پایش
کنید. سیاست حذف و نگهداری باید نسخهٔ سرور، فایل‌های بازیابی سرد و دانلودهای
محلی را هم پوشش دهد؛ حذف رکورد یک مدرسه مساوی پاک‌شدن تمام نسخه‌های آفلاین نیست.

## نگهداری و حذف محتوای تجاری

پس از توافق مهلت نگهداری با مدرسه، اپراتور می‌تواند درخواست تماسِ رسیدگی‌شده،
محتوای تیکت بستهٔ قدیمی و ایمیلِ ارسال‌شدهٔ قدیمی را بررسی و پاک‌سازی کند.
سفارش، پرداخت، صورتحساب، حساب مدرسه و audit مالی با این دستور حذف نمی‌شوند؛
محتوای تیکت باز یا ایمیل ارسال‌نشده نیز خودکار کنار گذاشته نمی‌شود.
ابتدا فقط گزارش را ببینید:

```sh
sudo docker compose --env-file deploy/.env -f deploy/compose.yml exec web python -m service.manage purge_business_content --days 365
```

اگر شمارش با سیاست مصوب سازگار بود و نسخهٔ بازیابی لازم را در محل امن
دارید، همان مهلت را با `--apply` اعمال کنید:

```sh
sudo docker compose --env-file deploy/.env -f deploy/compose.yml exec web python -m service.manage purge_business_content --days 365 --apply
```

بازهٔ مجاز دستور ۳۰ تا ۳۶۵۰ روز است؛ `365` نمونهٔ اجرایی است، نه حکم قانونی
برای همهٔ مدارس. متن پیام/پاسخ و اطلاعات تماس قدیمی ناشناس‌سازی می‌شوند و
ایمیل‌های واقعاً ارسال‌شدهٔ قدیمی حذف می‌شوند. تیکت بسته ممکن است در اجرای
بعد دوباره شمارش شود؛ عملیات روی متن حذف‌شده idempotent است. اگر تیکت قبلاً
پاک‌سازی‌شده دوباره باز و بعد بسته شود، پیام تازه هم پس از گذشت مهلتِ چرخهٔ
جدید باید پاک‌سازی شود. قفل تراکنشی والد مانع حذف پیام تازهٔ در حال بازشدن
در همان لحظهٔ اجرای retention می‌شود.

این پاک‌سازی به بکاپ‌های سرد سرور، ایمیل دریافتی مشتری یا فایل‌های دانلودشده
تسرّی پیدا نمی‌کند. دورهٔ حذف آن نسخه‌ها را جداگانه اجرا و مستند کنید.
اعلان pending یا دارای تلاش تمام‌شده را اپراتور بررسی کند؛ نگهداری آن دلیل
تحویل موفق یا مجوز نگهداری نامحدود اطلاعات نیست. هیچ وضعیت مالی را صرفاً
برای تحویل ایمیل دوباره فعال یا تأیید نکنید. SMTP پس از پذیرش پیام و پیش از
ثبت `sent_at` ممکن است قطع شود؛ اعلان‌ها ممکن است تکرار شوند، اما پرداخت و
صدور استحقاق باید از مسیر idempotent مستقل بماند.

## بازیابی، حریم خصوصی و آماده‌سازی پایلوت

همان `deploy/backup-server.sh` از PostgreSQL، blobها، فایل‌های release، کلیدهای
اصلی و commit یک بستهٔ age-encrypted می‌گیرد. کلید خصوصی age خارج از VPS نگهداری شود.
روزانه نسخهٔ خارج VPS و دوره‌ای تمرین restore روی مقصد تازه داشته باشید؛
بدون حساب واقعیِ مقصد، انتقال بیرونی خودکار تنظیم نشده است. مهاجرت‌های
دیتابیس فقط بعد از بکاپ بررسی‌شده اجرا شوند. کلید Ed25519 و master backup
را در upgrade دوباره تولید نکنید. بستهٔ جدید علاوه بر `blobs.tar`، فایل `releases.tar` دارد. پس از بازیابی
دیتابیس و blobها طبق راهنمای اشتراک، روی VPS تازه آن را با دسترسی اپراتور
در `deploy/releases/` باز کنید، چون mount داخل وب فقط‌خواندنی است:

```sh
sudo mkdir -p deploy/releases
sudo tar -C deploy/releases -xf recovery/releases.tar
```

بسته‌های قدیمی ممکن است این عضو را نداشته باشند؛ آن‌ها همچنان دیتابیس و
بکاپ مدارس را بازیابی می‌کنند ولی artifact باید از آرشیو انتشارِ تأییدشده
جداگانه برگردد. metadata دیتابیس به‌تنهایی فایل دانلود سالم ایجاد نمی‌کند.
برای staging چند برابر حجم DB، blob و release فضای آزاد لازم است؛ نگهداری
نسخه‌های بزرگ را متناسب با دیسک واقعی برنامه‌ریزی کنید.

هیچ تصویر چهره‌ای برای بازاریابی یا دمو فرستاده نمی‌شود. بکاپ دادهٔ چهره
فقط با رضایت صریح و کلید متعلق به مدرسه انجام می‌شود. در تیکت‌ها و درخواست
تماس، نام/عکس/شناسهٔ دانش‌آموز واقعی نگذارید. قبل از پایلوت، مسئول مجاز مدرسه
هدف پردازش، رضایت‌های لازم، دسترسی کارکنان، دورهٔ نگهداری، حذف و متولی کلید
بازیابی را تأیید کند. دادهٔ SQLite/CSV/rollback محلی هنوز به حساب ویندوز، ACL
محدود و ترجیحاً BitLocker متکی است؛ ادعای ضدکرک یا امنیت صددرصد نداریم.

چک‌لیست انتشار و Sama Cup:

- دمو و screenshot فقط با دادهٔ مصنوعی و نشان واضح «نمایشی» تهیه شوند.
- ثبت‌نام تا سفارش، رد و تأیید پرداخت، صورتحساب و صدور entitlement را با
  حساب آزمایشی کامل کنید؛ هیچ پرداخت تأییدنشده‌ای نباید اشتراک بسازد.
- مالک، کاربر staff/superuser بدون ownership و دو مدرسهٔ جدا را برای کنترل
  دسترسی دستگاه/بکاپ/سفارش/صورتحساب/تیکت/دانلود امتحان کنید.
- فعال‌سازی یک‌باره، reboot و شروع بدون اینترنت، sleep/resume، انقضا، تمدید
  و لغو پس از اتصال را روی Windows واقعی بررسی کنید.
- برابری دو دوربین، OSNet و رویدادها را با مبنای شناخته‌شده بررسی کنید؛ از
  سرعت یا کیفیتِ اندازه‌گیری‌نشده روی CPU ضعیف ادعا نسازید.
- کلید مدرسه را جدا نگه دارید، بکاپ کامل را روی نصب دوم بازیابی و عکس‌ها،
  تنظیمات و سوابق را بررسی کنید. دیسک‌پر/قطع عملیات را فقط روی کپی آزمایشی تست کنید.
- HTTPS/SMTP واقعی، حمایت پاسخ‌گویی، قرارداد/حریم خصوصی، شرایط پرداخت،
  مالکیت نام/نشان و مجوز توزیع مدل‌ها را قبل از مشتری واقعی نهایی کنید.
