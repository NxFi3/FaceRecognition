# راه‌اندازی حساب مدرسه، اشتراک و بکاپ آنلاین

> برای پلتفرم تجاریِ شاخهٔ `feature/nxfi-commercial-platform`، ایجاد مالک،
> خرید/صورتحساب و انتشار فایل ابتدا [راهنمای تجاری](commercial-deployment-fa.md)
> را بخوانید. دستور قدیمی `createsuperuser` به‌تنهایی مجوز مالک ایجاد نمی‌کند.
> بخش‌های مجوز آفلاین و بازیابی این راهنما همچنان کاربرد دارند.

این نسخه روی شاخهٔ جداگانهٔ `hardening/offline-first-licensing` از مبنای تأییدشدهٔ `5f6bd20` ساخته شده است. ورود
سایت، اشتراک و بکاپ از مسیر دوربین و مدل‌ها جدا هستند. منطق تطبیق چهره،
تأیید هویت، Re-ID و آستانه‌های آن‌ها تغییر نکرده است.

فعلاً پرداخت دستی است: مدرسه حساب می‌سازد، شما پرداخت را بررسی می‌کنید و
تاریخ و ظرفیت را از پنل فعال می‌کنید. اتصال درگاه ایرانی به حساب پذیرندگی
و پیاده‌سازی تأیید پرداخت سمت سرور نیاز دارد؛ در این نسخه پرداخت خودکار
یا درگاه نمایشی وجود ندارد.

## ۱. چه چیزی تهیه کنید

- یک دامنه یا زیردامنه، مثلاً `schools.yourbrand.ir`.
- VPS با Ubuntu 24.04، IP عمومی ثابت و Docker. نقطهٔ شروع پیشنهادی: ۲ هسته،
  ۴ گیگابایت RAM و حداقل ۴۰ گیگابایت SSD. این اعداد پیشنهاد اجرایی‌اند و
  ظرفیت‌سنجی واقعی برای تعداد مشخصی مدرسه نیستند.
- سرویس SMTP با STARTTLS روی پورت ۵۸۷ و فرستندهٔ تأییدشده برای تأیید ایمیل
  و بازیابی رمز. صرف داشتن VPS، تحویل مطمئن ایمیل ایجاد نمی‌کند.
- فضای جدا از VPS برای نگهداری نسخهٔ بازیابی خودِ سرور.

دوربین و تشخیص روی کامپیوتر مدرسه اجرا می‌شوند؛ VPS مدل‌های بینایی را اجرا
نمی‌کند. مصرف اصلی فضای سرور، بکاپ مدارس است. برای هر مدرسه پیش‌فرض یک
گیگابایت سهمیه و هفت نسخهٔ اخیر وجود دارد؛ مجموع سهمیه‌ها را با دیسک واقعی
سرور هماهنگ کنید.

رکورد DNS نوع A دامنه را به IP سرور متصل کنید. دسترسی ورودی ۸۰ و ۴۴۳ و
پورت SSH خودتان، و خروجی HTTPS/SMTP باید مجاز باشد. پورت PostgreSQL، Redis
یا Gunicorn را روی اینترنت منتشر نکنید. Compose فقط پورت‌های Caddy را
منتشر می‌کند و Caddy گواهی HTTPS را دریافت و تمدید می‌کند.

## ۲. آماده‌سازی VPS

روی سرور تازه، ابتدا Git را نصب و مخزن را دریافت کنید:

```sh
sudo apt-get update
sudo apt-get install -y git
git clone --branch hardening/offline-first-licensing https://github.com/NxFi3/FaceRecognition.git
cd FaceRecognition
sudo ./deploy/install-ubuntu.sh schools.yourbrand.ir owner@yourbrand.ir
```

دو مقدار نمونه را با دامنه و ایمیل خودتان عوض کنید. اسکریپت برای Ubuntu
24.04 است؛ روی سیستم‌عامل دیگر Docker Compose و Python را طبق مستندات رسمی
نصب و دستور تولید تنظیمات را اجرا کنید:

```sh
python -m pip install -r requirements-cloud.txt
python -m deploy.configure --domain schools.yourbrand.ir --email owner@yourbrand.ir
```

خروجی‌ها:

- `deploy/.env`: رمز دیتابیس، کلید امضای لایسنس، کلید رمزگذاری بکاپ و تنظیمات
  سرویس. **محرمانه است؛ به مشتری ندهید و در Git ثبت نکنید.**
- `deploy/generated/subscription-client.json`: فقط آدرس سرویس و کلید عمومی.
  این فایل برای بستهٔ دسکتاپ همهٔ مشتری‌ها یکسان و قابل انتشار است.

اسکریپت عمداً `.env` موجود را بازنویسی نمی‌کند. حذف و تولید دوبارهٔ کلید
بکاپ باعث غیرقابل‌خواندن شدن بکاپ‌های قبلی می‌شود. ارتقای برنامه به تولید
دوبارهٔ کلیدها نیاز ندارد.

فایل `deploy/.env` را با دسترسی مدیر ویرایش کنید:

```sh
sudo nano deploy/.env
```

مقادیر `SMTP_HOST`، `SMTP_USER`، `SMTP_PASSWORD` و `SMTP_FROM` را مطابق سرویس
ایمیل پر کنید. `SMTP_FROM` باید فرستندهٔ تأییدشدهٔ شما باشد. برای مقدار رمز
حاوی `$` از نقل‌قول تکی مطابق قالب dotenv در Compose استفاده کنید. رمزها را
در پیام، اسکرین‌شات یا تیکت عمومی قرار ندهید. تا وقتی SMTP تنظیم نشده،
ثبت‌نام عمومی با پیام مشخص غیرفعال می‌ماند؛ پنل مدیر قابل راه‌اندازی است.

سپس:

```sh
sudo docker compose --env-file deploy/.env -f deploy/compose.yml config --quiet
sudo docker compose --env-file deploy/.env -f deploy/compose.yml up -d --build
sudo docker compose --env-file deploy/.env -f deploy/compose.yml ps
sudo docker compose --env-file deploy/.env -f deploy/compose.yml exec web python -m service.manage createsuperuser
```

حساب مدیر پیش‌فرض و رمز عمومی ساخته نمی‌شود. نام کاربری، ایمیل و رمز مدیر
را در دستور آخر خودتان وارد کنید. سپس `https://دامنه/admin/` را باز کنید.
آدرس `https://دامنه/health/` باید `{"ok": true}` برگرداند؛ این بررسی سلامت
دیتابیس و Redis است، نه تضمین تحویل ایمیل یا فضای کافی دیسک.

## ۳. فروش و فعال کردن مدرسه

۱. مدرسه در `/register/` ثبت‌نام می‌کند و لینک تأیید ایمیل را باز می‌کند.
۲. پس از پرداخت، شما در `/admin/` بخش «مدارس» حساب آن مدرسه را پیدا می‌کنید.
۳. وضعیت را «فعال»، ظرفیت را مثلاً `900` و تعداد دستگاه را مثلاً `1` می‌گذارید.
۴. شروع و پایان اشتراک را ثبت می‌کنید؛ تاریخ‌های پنل **میلادی و UTC** هستند.
   برای زمان تهران، اختلاف منطقهٔ زمانی را لحاظ کنید. برای قرارداد یک‌ساله،
   تاریخ پایان واقعی قرارداد را انتخاب کنید.
۵. بکاپ را مجاز و تعداد نسخه‌ها/سهمیهٔ فضای مدرسه را تنظیم و ذخیره می‌کنید.

«ظرفیت» تعداد رکوردهای فعالِ فهرست ظرفیت است. رکوردهای قدیمی در مهاجرت
همگی فعال باقی می‌مانند. از صفحهٔ اشتراک، «مدیریت فهرست فعال / آرشیو ظرفیت»
را باز کنید و وضعیت هر دانش‌آموز را صریحاً تغییر دهید. آرشیو هیچ رکورد،
چهره یا سابقه‌ای را حذف نمی‌کند. برای حفظ رفتار مبنا، **آرشیو در این پایلوت
تشخیص فرد و تصمیم حضور و غیاب او را غیرفعال نمی‌کند**؛ این گزینه صرفاً
طبقه‌بندی فهرست قرارداد است، نه ابزار قطع شناسایی یا حفاظت ضدکرک.
فعال‌سازی دوباره و ثبت دانش‌آموز جدید به ظرفیت آزاد نیاز دارند. کاهش ظرفیت
هیچ داده‌ای را حذف یا از دسترس خارج نمی‌کند؛ تا آزادشدن ظرفیت، ثبت/فعال‌سازی
جدید رد می‌شود. تنظیم ظرفیت صفر، تعلیق اشتراک است.

برای تمدید فقط پایان اشتراک را جلو ببرید. برای تعلیق یا مسدودسازی، وضعیت
را تغییر دهید. برای تعویض کامپیوتر، دستگاه قبلی را از پنل لغو کنید تا نصب
جدید ظرفیت دستگاه را اشغال کند. دستگاهی که صریحاً لغو شده است تا رفع لغو
توسط مدیر دوباره وارد نمی‌شود؛ تغییر رمز هم اعتبار دستگاه‌های قبلی را رد
می‌کند و ورود مجدد لازم است.

حساب مشتری را staff یا superuser نکنید. مشتری فقط صفحهٔ حساب، اشتراک،
دستگاه‌های خودش و بکاپ‌های خودش را می‌بیند. رویدادهای تغییر اشتراک، ورود و
لغو دستگاه و عملیات بکاپ در پنل ثبت می‌شوند.

## ۴. ساخت و تحویل ویندوز

فایل عمومی `deploy/generated/subscription-client.json` را کنار
`buildwindows.bat` قرار دهید. این فایل فقط نشانی HTTPS و کلید عمومی Ed25519
دارد. `.env` و کلید خصوصی امضا هرگز نباید وارد بستهٔ مشتری شوند.

روی Windows x64 و Python 3.11، یک محیط تازه بسازید. از wheel سازگار dlib
استفاده کنید؛ CI از `dlib-bin==20.0.1.post1` استفاده می‌کند. وابستگی‌های
`requirements.txt` و PyInstaller 6 را نصب کنید؛ اگر نصب dlib از سورس برایتان
ممکن نیست، مانند workflow ردیف‌های `dlib` و `face_recognition` را از فایل
موقت نیازمندی‌ها کنار بگذارید، `dlib-bin` را اول نصب و سپس
`face_recognition --no-deps` را با `click` و `Pillow` نصب کنید.

برای مدرسه‌ای که مبنای آزمایش‌شده‌اش OSNet دارد، همان وابستگی‌های CPU
`requirements-reid.txt` و **همان وزن‌های cache‌شدهٔ مبنا** را آماده کنید؛
هیچ مدل جدیدی برای تحویل جایگزین نکنید. مسیر TORCH_HOME موجود را بدهید:

```bat
set FACE_REID_CACHE=C:\secure-build-assets\torch
buildwindows.bat
```

این پوشه باید `hub\checkpoints\*osnet*x0_25*.pth` داشته باشد. بسته cache را
در `models/torch/` می‌گذارد و Torch/Torchvision/TorchReID را جمع می‌کند.
تنها اگر مبنای مدرسه اصلاً OSNet نداشته، صریحاً `FACE_ALLOW_NO_REID=1` را تنظیم
کنید. حذف خاموش Re-ID از بسته مجاز نیست. شاخهٔ CI بدون وزن‌های تأییدشدهٔ
OSNet فقط با repository variable برابر
`RELEASE_REID_POLICY=not-used-in-pilot` بسته می‌سازد؛ در غیر این صورت از ساخت
محلی کامل استفاده کنید. متغیرهای عمومی `CLOUD_SERVICE_URL` و
`CLOUD_PUBLIC_KEY` نیز برای CI لازم‌اند.

Manifest فایل `models/runtime-assets.json` شامل hash دارایی‌ها و نسخه‌های
وابستگی‌هاست؛ همراه release و محیط ساخت نگه دارید. برای بازتولید همان release
از همان Python، وابستگی‌ها و hashها استفاده کنید. مدل‌های dlib همان فایل‌های
بستهٔ `face_recognition_models==0.3.0` هستند؛ locator جدید فقط وابستگی منسوخ
`pkg_resources` را حذف می‌کند و اجازهٔ استفاده از setuptools اصلاح‌شده را می‌دهد.

**ساخت واقعی ویندوز، امضای EXE و آزمایش دوربین در این محیط انجام نشده‌اند.**
پوشهٔ کامل خروجی را منتقل کنید، نه فقط EXE. برنامه را در پوشهٔ مخصوص حساب
ویندوز مدرسه با ACL محدود نصب کنید؛ Credential Manager و مجوز آفلاین به
همان حساب کاربری وابسته‌اند. روی حساب جدید، فعال‌سازی آنلاین مجدد لازم است.
فایل‌های SQLite، CSV و نسخه‌های rollback محلی رمزگذاری سرتاسری نمی‌شوند؛
ACL، حساب اختصاصی، رمز ویندوز و BitLocker را متناسب با سیاست مدرسه اعمال کنید.

## ۵. فعال‌سازی آفلاین‌محور، انقضا و تمدید

۱. یک بار با اینترنت، ایمیل و رمز حساب سایت مدرسه وارد شوید. برنامه مجوز
نسخهٔ ۲ را با امضای Ed25519 و اتصال به UUID مدرسه و نصب دریافت می‌کند.
۲. رمز محلی مدیرِ برنامه جدا از رمز سایت است. پیش از اتصال اولین دیتابیس،
نام مدرسه را تأیید کنید. دیتابیس مدرسهٔ دیگر رد می‌شود.
۳. مجوز و checkpoint زمان در مخزن امن سیستم‌عامل ذخیره می‌شوند؛ هیچ کلید
خصوصی امضا روی دسکتاپ نیست. بدون خزانهٔ امنِ فعال، فعال‌سازی آفلاین انجام
نمی‌شود. Windows Credential Manager یا خزانهٔ امن پشتیبانی‌شدهٔ Linux را
در همان حساب کاربری باز و فعال نگه دارید.
۴. پس از فعال‌سازی، اینترنت را قطع و چند بار برنامه را ببندید و باز کنید.
تا پایان تاریخ امضاشده، دوربین، ثبت چهره، حضور و غیاب و گزارش محلی باید کار
کنند. شروع عادی منتظر سرور نمی‌ماند. صفحهٔ اشتراک محلی پیش از دوربین همچنان
برای امکان بازیابی نمایش داده می‌شود؛ هیچ درخواست شبکه‌ای خودکار در آن لازم نیست.
۵. همگام‌سازی چند ثانیه پس از بازشدن محیط اصلی در thread پس‌زمینه تلاش
می‌شود؛ پس از موفقیت هر یک ساعت. پس از خطا فاصلهٔ تلاش‌ها به‌صورت نمایی از
حدود دو دقیقه تا یک ساعت افزایش می‌یابد. خطای شبکه یا پاسخ HTTP بدون مدرک
امضاشدهٔ لغو، مجوز آفلاین معتبر را باطل نمی‌کند.
۶. برای تمدید، پس از تأیید پرداخت دستی، در پنل تاریخ پایان را جلو ببرید و
وضعیت را فعال نگه دارید. در برنامه «بررسی / تمدید آنلاین و ورود دوباره»
را بزنید یا منتظر همگام‌سازی شوید. بعد از انقضا هم از صفحهٔ ورود همین کار
را انجام دهید. مجوز تازه تا پایان دورهٔ جدید آفلاین کار می‌کند؛ چرخه محدود
به یک تمدید نیست. با تغییر رمز حساب سایت ممکن است ورود مجدد لازم شود.

وقتی مجوز منقضی یا لغو شود، دوربین متوقف و محیط عملیاتی بسته می‌شود؛ داده
پاک نمی‌شود. در اجرای بعد با رمز مدیر محلی به «خروجی / بازیابی محلی اطلاعات
مدرسه» دسترسی دارید: خروجی CSV حضور و غیاب، بکاپ کامل رمزگذاری‌شده و بازیابی
بکاپ محلی با کلید مدرسه. همچنین از سایت، تا وقتی حساب کاربر فعال است، بکاپ‌های
قبلی را حتی پس از انقضای اشتراک دریافت کنید. CSV خروجی ساده است، جایگزین
همهٔ داشبوردهای برنامه در حالت منقضی نیست.

عقب‌بردن مشکوک ساعت نسبت به checkpoint، دستکاری مجوز یا rollback ناسازگار
وضعیت، بررسی آنلاین تازه می‌خواهد. ساعت سرور باید با NTP تنظیم باشد. تحمل
تغییر جزئی ساعت پنج دقیقه است؛ زمان سرور، زمان سپری‌شدهٔ یکنواخت و مشاهدهٔ
محلی با هم استفاده می‌شوند. این حفاظت TPM یا ضدکرک مطلق نیست؛ snapshot کامل
سیستم یا دستکاری برنامه توسط مالکِ دارای دسترسی مدیر، قابل تضمین نیست.

**یک سال اعتبار آفلاین با لغو آنی از راه دور قابل جمع نیست.** دستگاهی که
اینترنت ندارد تا انقضای امضاشده می‌تواند کار کند. لغو مدرسه/دستگاه در اتصال
موفق بعدی با پاسخ امضاشده اعمال می‌شود. آزادکردن یک slot برای دستگاه جدید،
نسخهٔ قدیمیِ کاملاً آفلاین را فوراً از کار نمی‌اندازد. تغییر رمز/چرخش توکن
ممکن است ورود آنلاین مجدد لازم کند و جایگزین دریافت وضعیت امضاشده نیست.

## ۶. بکاپ، کلید بازیابی، نگهداری و حذف

بکاپ کاملاً اختیاری است. ارسال روزانه فقط با انتخاب صریح گزینهٔ رضایت
مدرسه فعال می‌شود؛ ارسال دستی هم تأیید می‌خواهد. رضایت شامل داده‌های چهره
و تصاویر رویداد است. **قبل از اولین بکاپ** از صفحهٔ اشتراک، «ذخیرهٔ کلید
بازیابی مدرسه در محل امن» را بزنید و فایل `.frkey` را روی حافظهٔ جداگانه و
محافظت‌شده نگه دارید. فایل کلید خودش بدون رمز است؛ هرکس کلید و بکاپ را با هم
داشته باشد می‌تواند آن را بخواند. کلید را به سرور یا تیکت پشتیبانی نفرستید.
یک نسخهٔ دوم را نزد مسئول مجاز مدرسه، جدا از دستگاه و بکاپ‌ها، نگه دارید.

کلید ۲۵۶بیتی مدرسه فقط در خزانهٔ امن سیستم و فایل بازیابی منتخب مدرسه است.
سرور آن را دریافت نمی‌کند. گرفتن خروجی دوباره همان کلید قبلی را می‌دهد؛
کلید متفاوت بی‌صدا جایگزین نمی‌شود. برای کامپیوتر جدید پس از فعال‌سازی همین
مدرسه، «واردکردن کلید بازیابی موجود» را بزنید. **گم‌شدن تمام نسخه‌های کلید
قابل جبران توسط فروشنده نیست.** بازیابی آزمایشی را پیش از اتکا به بکاپ انجام دهید.

بکاپ جدید `.frbackup` شامل snapshot دیتابیس SQLite، همهٔ تنظیمات دیتابیس،
دانش‌آموزان، embeddings، حضور، رویدادها، هش رمز مدیر و فایل‌های فعلی
`data/early_exit_review/event_*.jpg` است. بسته ابتدا با AES-256-GCM و AAD مدرسه
در خود برنامه رمزگذاری و سپس با HTTPS ارسال می‌شود. سرور ciphertext را
ذخیره و یک لایهٔ رمزگذاری سروری هم روی آن اعمال می‌کند؛ داشتن کلید سرور
برای خواندن لایهٔ داخلی جدید کافی نیست. مجوز/توکن/کلید بازیابی و مدل‌ها داخل
بکاپ نیستند؛ نصب مجدد برنامه و فعال‌سازی جداگانه لازم است. برای snapshot
کاملاً هماهنگ عکس‌های در حال ذخیره با دیتابیس، خروجی محلی را پس از توقف برنامه
بگیرید؛ بکاپ زنده ممکن است آخرین عکسی را که هنوز نوشته نشده شامل نشود.

بکاپ قدیمی SQLite، با همان کلید اصلی سرور و روش قبلی قابل دریافت و بازیابی
می‌ماند؛ تصاویر خارجی ندارد و اپراتور سرور می‌تواند آن را رمزگشایی کند.
مهاجرت خودکار یا حذف نسخه‌های قدیمی انجام نمی‌شود؛ برای نسخهٔ جدید، بعد از
ثبت کلید مدرسه یک بکاپ تازه بگیرید و طبق رضایت مدرسه قدیمی‌ها را جداگانه حذف کنید.

سقف هر فایل رمزگذاری‌شدهٔ ابری همان **۱۲۸ MiB** است؛ حد کورکورانه بالا نرفته.
برای بررسی اندازهٔ دادهٔ واقعی، بدون خروج اطلاعات شخصی اجرا کنید:

```sh
python -m tools.backup_inventory --database data/attendance.db
```

فهرست تعداد/حجم است، نه تضمین اندازهٔ فشرده. اندازهٔ نهایی قبل از upload
بررسی می‌شود؛ بزرگ‌بودن خطای صریح می‌دهد و دادهٔ محلی حفظ می‌شود. برای
فایل بزرگ، فعلاً خروجی کامل محلی بگیرید؛ افزایش حد سرور مستلزم بررسی سهمیه،
فضای tmpfs و proxy است. اندازه‌گیری fixture مصنوعی ۹۰۰نفری در یادداشت فنی
آمده و جایگزین اندازه‌گیری عکس‌های مدرسه نیست.

پیش‌فرض سرور هفت نسخه و یک GiB سهمیه برای هر مدرسه است. نسخهٔ قدیمی فقط پس
از ثبت موفق نسخهٔ جدید حذف می‌شود. صاحب حساب می‌تواند بکاپ منتخب خود را از
سایت حذف کند؛ درخواست مدرسهٔ دیگر رد می‌شود. حذف از سرویس، نسخه‌های مستقل
بکاپ سرد سرور یا فایل دانلودشده را از بین نمی‌برد. برای پایلوت، مسئول نگهداری
سرور باید سیاست نمونهٔ «هفت نسخهٔ روزانهٔ بکاپ سرور و حذف staging پس از
بازیابی» را در برنامهٔ عملیاتی اجرا کند؛ اسکریپت انتقال/حذف بیرون VPS بدون
مقصد واقعی خودکار پیکربندی نشده است. مهلت نهایی حذف داده را با مدرسه توافق کنید.

بازیابی آنلاین: برنامه را دوباره باز کنید، **پیش از ورود به محیط دوربین**
در صفحهٔ اشتراک فهرست بکاپ‌ها را بگیرید؛ کلید همین مدرسه باید وارد شده باشد.
فایل از نظر hash، GCM، مدرسه، مسیرهای ZIP و سلامت SQLite بررسی می‌شود؛ سپس
دیتابیس و تصاویر جایگزین می‌شوند. نسخهٔ قبل در `data/before-restore-*/` حفظ
می‌شود. اگر فرایند وسط جایگزینی قطع شود، journal در شروع بعدی وضعیت قبلی را
بازیابی می‌کند. نسخه‌های rollback و staging محلی حساس‌اند؛ بعد از تأیید
موفقیت طبق سیاست مدرسه حذف شوند. پس از restore رمز مدیر محلی دوباره بررسی می‌شود.

خروجی/بازیابی مستقل از اشتراک با برنامهٔ بسته و محیط Python نصب‌شده:

```sh
python -m tools.school_recovery csv --database data/attendance.db --output attendance.csv
python -m tools.school_recovery export --database data/attendance.db --key school.frkey --output school.frbackup
python -m tools.school_recovery restore --database data/attendance.db --key school.frkey --input school.frbackup
python -m tools.school_recovery recover-interrupted --database data/attendance.db
```

این ابزار به اینترنت نیاز ندارد؛ روی دیتابیس موجود و متصل به همان مدرسه
کار می‌کند و قفل اجرای برنامه را می‌گیرد. فرمان restore جایگزینی عمدی داده
است؛ ابتدا خروجی ایمن بگیرید. حتی بدون فایل تنظیم عمومی سرویس، ابزار CSV و
بکاپ محلی برای حفظ مالکیت داده قابل استفاده است.

## ۷. بکاپ خودِ سرور و بازیابی VPS

بکاپ مدارس روی همان VPS، جایگزین بکاپ خود سرور نیست. روی یک دستگاه امن
جداگانه با `age-keygen -o recovery.key` یک هویت بازیابی بسازید و کلید خصوصی
آن را خارج از VPS نگه دارید. فقط گیرندهٔ عمومی `age1...` را به VPS بدهید:

```sh
sudo ./deploy/backup-server.sh age1YOUR_PUBLIC_RECIPIENT /secure/offsite/server-2026-10-23.age
```

`age` توسط helper اوبونتو نصب می‌شود. مسیر خروجی باید موجود و فضای آزاد
کافی باشد. سرویس وب هنگام snapshot سازگار، موقتاً متوقف و سپس دوباره شروع
می‌شود؛ دوربین‌های دارای مجوز معتبر تا مهلت خود ادامه می‌دهند. فایل شامل
PostgreSQL، blobهای رمزگذاری‌شده، `.env` و شناسهٔ commit است و با کلید عمومی
بازیابی رمزگذاری می‌شود. برای staging چند برابر حجم بکاپ فضای آزاد در نظر
بگیرید. فایل نهایی را واقعاً به فضای خارج از VPS کپی کنید و یک بار بازیابی
را آزمایش کنید. ارسال خودکار به ارائه‌دهندهٔ فضای بیرونی بدون حساب آن
ارائه‌دهنده پیکربندی نشده است.

بازیابی روی VPS **تازه و بدون دادهٔ تولیدی**:

۱. با کلید خصوصی روی دستگاه امن، بسته را باز کنید:

```sh
age -d -i recovery.key -o recovery.tar server-2026-10-23.age
mkdir -m 700 recovery
tar -xf recovery.tar -C recovery
```

۲. مخزن را در commit نوشته‌شده در `code-version.txt` دریافت و `server.env`
را با مجوز `600` در `deploy/.env` بگذارید؛ کلید جدید تولید نکنید.
۳. image را بسازید و فقط دیتابیس و Redis را شروع کنید:

```sh
sudo docker compose --env-file deploy/.env -f deploy/compose.yml build db web
sudo docker compose --env-file deploy/.env -f deploy/compose.yml up -d db redis
```

۴. پس از سالم شدن دیتابیس، داده را فقط در مقصد تازه بازیابی کنید:

```sh
sudo docker compose --env-file deploy/.env -f deploy/compose.yml exec -T db pg_restore -U face_service -d face_service --clean --if-exists --no-owner --exit-on-error < recovery/database.dump
sudo docker compose --env-file deploy/.env -f deploy/compose.yml run --rm --no-deps -T web tar -C /data/backups -xf - < recovery/blobs.tar
sudo docker compose --env-file deploy/.env -f deploy/compose.yml up -d
```

۵. DNS، HTTPS، ورود یک مدرسه و دریافت یک بکاپ را بررسی کنید. فایل‌های
رمزگشایی‌شدهٔ بازیابی، به‌خصوص `server.env`، محرمانه‌اند و پس از پایان کار
باید از محل staging حذف شوند.

## ۸. نگهداری و محدودهٔ تأیید

قبل از ارتقا، بکاپ سرور بگیرید؛ سپس کد را به نسخهٔ بازبینی‌شده ارتقا دهید و
`up -d --build` اجرا کنید. `.env` و کلیدها را حفظ کنید. لاگ‌ها:

```sh
sudo docker compose --env-file deploy/.env -f deploy/compose.yml logs --tail 100 web
sudo docker compose --env-file deploy/.env -f deploy/compose.yml exec web python -m service.manage check --deploy --fail-level WARNING
sudo docker compose --env-file deploy/.env -f deploy/compose.yml exec web python -m service.manage prune_backup_orphans
```

دستور آخر dry-run است؛ `--apply` فقط فایل‌های بدون رکورد و قدیمی‌تر از یک
روز را پاک می‌کند. این کار برای بقایای قطع برق/آپلود نیمه‌تمام است. فضای
دیسک، سلامت سرویس، تحویل ایمیل، تمدید گواهی و بکاپ خارج VPS را پایش کنید.
HSTS فقط برای همان hostname فعال است؛ دو توصیهٔ Django برای preload و اجبار
HTTPS همهٔ زیردامنه‌ها عمداً اعمال نشده‌اند تا دامنه‌های دیگر شما خراب نشوند.

هیچ نرم‌افزار دسکتاپی در برابر مالک کامپیوتر که کد اجرایی را تغییر دهد،
ضدکرک مطلق نیست. در این نسخه، تصمیم اشتراک سروری، توکن تصادفی قابل لغو،
کلید عمومی ثابت و مجوز امضاشده تا پایان اشتراک استفاده شده است. این کنترل‌ها جای امضای
کد انتشار، امنیت VPS، نگهداری کلیدها یا ارزیابی امنیت مستقل را نمی‌گیرند.
تست خودکار، تضمین «صفر باگ امنیتی» یا تأیید عملکرد روی همهٔ دوربین‌ها نیست.
قبل از فروش، HTTPS واقعی، SMTP واقعی، بستهٔ EXE امضاشده و سناریوی دو دوربین
را روی نصب آزمایشی بررسی کنید. نتیجهٔ تست‌های انجام‌شده در
[یادداشت فنی](subscription-technical.md) ثبت می‌شود.
