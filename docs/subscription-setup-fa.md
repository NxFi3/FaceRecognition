# راه‌اندازی حساب مدرسه، اشتراک و بکاپ آنلاین

این نسخه روی شاخهٔ `fix/enrollment-dialog-responsive` ساخته شده است. ورود
سایت، اشتراک و بکاپ از مسیر دوربین و مدل‌ها جدا هستند. منطق تطبیق چهره،
تأیید هویت، Re-ID و آستانه‌های آن‌ها تغییر نکرده است.

فعلاً پرداخت دستی است: مدرسه حساب می‌سازد، شما پرداخت را بررسی می‌کنید و
تاریخ و ظرفیت را از پنل فعال می‌کنید. اتصال درگاه ایرانی به حساب پذیرندگی
و پیاده‌سازی تأیید پرداخت سمت سرور نیاز دارد؛ در این نسخه پرداخت خودکار
یا درگاه نمایشی وجود ندارد.

## ۱. چه چیزی تهیه کنید

- یک دامنه یا زیردامنه، مثلاً `schools.yourbrand.ir`.
- VPS با Ubuntu 24.04، IP عمومی ثابت و Docker. نقطهٔ شروع پیشنهادی: ۲ هسته،
  ۴ گیگابایت RAM و حداقل ۴۰ گیگابایت SSD. این اعداد پیشنهاد اجرایی‌اند و
  ظرفیت‌سنجی واقعی برای تعداد مشخصی مدرسه نیستند.
- سرویس SMTP با STARTTLS روی پورت ۵۸۷ و فرستندهٔ تأییدشده برای تأیید ایمیل
  و بازیابی رمز. صرف داشتن VPS، تحویل مطمئن ایمیل ایجاد نمی‌کند.
- فضای جدا از VPS برای نگهداری نسخهٔ بازیابی خودِ سرور.

دوربین و تشخیص روی کامپیوتر مدرسه اجرا می‌شوند؛ VPS مدل‌های بینایی را اجرا
نمی‌کند. مصرف اصلی فضای سرور، بکاپ مدارس است. برای هر مدرسه پیش‌فرض یک
گیگابایت سهمیه و هفت نسخهٔ اخیر وجود دارد؛ مجموع سهمیه‌ها را با دیسک واقعی
سرور هماهنگ کنید.

رکورد DNS نوع A دامنه را به IP سرور متصل کنید. دسترسی ورودی ۸۰ و ۴۴۳ و
پورت SSH خودتان، و خروجی HTTPS/SMTP باید مجاز باشد. پورت PostgreSQL، Redis
یا Gunicorn را روی اینترنت منتشر نکنید. Compose فقط پورت‌های Caddy را
منتشر می‌کند و Caddy گواهی HTTPS را دریافت و تمدید می‌کند.

## ۲. آماده‌سازی VPS

روی سرور تازه، ابتدا Git را نصب و مخزن را دریافت کنید:

```sh
sudo apt-get update
sudo apt-get install -y git
git clone --branch fix/enrollment-dialog-responsive https://github.com/NxFi3/FaceRecognition.git
cd FaceRecognition
sudo ./deploy/install-ubuntu.sh schools.yourbrand.ir owner@yourbrand.ir
```

دو مقدار نمونه را با دامنه و ایمیل خودتان عوض کنید. اسکریپت برای Ubuntu
24.04 است؛ روی سیستم‌عامل دیگر Docker Compose و Python را طبق مستندات رسمی
نصب و دستور تولید تنظیمات را اجرا کنید:

```sh
python -m pip install -r requirements-cloud.txt
python -m deploy.configure --domain schools.yourbrand.ir --email owner@yourbrand.ir
```

خروجی‌ها:

- `deploy/.env`: رمز دیتابیس، کلید امضای لایسنس، کلید رمزگذاری بکاپ و تنظیمات
  سرویس. **محرمانه است؛ به مشتری ندهید و در Git ثبت نکنید.**
- `deploy/generated/subscription-client.json`: فقط آدرس سرویس و کلید عمومی.
  این فایل برای بستهٔ دسکتاپ همهٔ مشتری‌ها یکسان و قابل انتشار است.

اسکریپت عمداً `.env` موجود را بازنویسی نمی‌کند. حذف و تولید دوبارهٔ کلید
بکاپ باعث غیرقابل‌خواندن شدن بکاپ‌های قبلی می‌شود. ارتقای برنامه به تولید
دوبارهٔ کلیدها نیاز ندارد.

فایل `deploy/.env` را با دسترسی مدیر ویرایش کنید:

```sh
sudo nano deploy/.env
```

مقادیر `SMTP_HOST`، `SMTP_USER`، `SMTP_PASSWORD` و `SMTP_FROM` را مطابق سرویس
ایمیل پر کنید. `SMTP_FROM` باید فرستندهٔ تأییدشدهٔ شما باشد. برای مقدار رمز
حاوی `$` از نقل‌قول تکی مطابق قالب dotenv در Compose استفاده کنید. رمزها را
در پیام، اسکرین‌شات یا تیکت عمومی قرار ندهید. تا وقتی SMTP تنظیم نشده،
ثبت‌نام عمومی با پیام مشخص غیرفعال می‌ماند؛ پنل مدیر قابل راه‌اندازی است.

سپس:

```sh
sudo docker compose --env-file deploy/.env -f deploy/compose.yml config --quiet
sudo docker compose --env-file deploy/.env -f deploy/compose.yml up -d --build
sudo docker compose --env-file deploy/.env -f deploy/compose.yml ps
sudo docker compose --env-file deploy/.env -f deploy/compose.yml exec web python -m service.manage createsuperuser
```

حساب مدیر پیش‌فرض و رمز عمومی ساخته نمی‌شود. نام کاربری، ایمیل و رمز مدیر
را در دستور آخر خودتان وارد کنید. سپس `https://دامنه/admin/` را باز کنید.
آدرس `https://دامنه/health/` باید `{"ok": true}` برگرداند؛ این بررسی سلامت
دیتابیس و Redis است، نه تضمین تحویل ایمیل یا فضای کافی دیسک.

## ۳. فروش و فعال کردن مدرسه

۱. مدرسه در `/register/` ثبت‌نام می‌کند و لینک تأیید ایمیل را باز می‌کند.
۲. پس از پرداخت، شما در `/admin/` بخش «مدارس» حساب آن مدرسه را پیدا می‌کنید.
۳. وضعیت را «فعال»، ظرفیت را مثلاً `900` و تعداد دستگاه را مثلاً `1` می‌گذارید.
۴. شروع و پایان اشتراک را ثبت می‌کنید؛ تاریخ‌های پنل **میلادی و UTC** هستند.
   برای زمان تهران، اختلاف منطقهٔ زمانی را لحاظ کنید. برای قرارداد یک‌ساله،
   تاریخ پایان واقعی قرارداد را انتخاب کنید.
۵. بکاپ را مجاز و تعداد نسخه‌ها/سهمیهٔ فضای مدرسه را تنظیم و ذخیره می‌کنید.

«ظرفیت» در این نسخه تعداد **تمام رکوردهای دانش‌آموز ذخیره‌شده در دیتابیس**
است، نه تعداد رویدادها، تصاویر یا تعداد افراد دیده‌شده. رکوردهای سال‌های
قبل هم حساب می‌شوند؛ آرشیو دانش‌آموزِ خارج از ظرفیت هنوز تعریف نشده است.
ظرفیت را بدون هماهنگی به کمتر از دادهٔ موجود کاهش ندهید. هیچ داده‌ای برای
انطباق با ظرفیت به‌طور خودکار حذف نمی‌شود.

برای تمدید فقط پایان اشتراک را جلو ببرید. برای تعلیق یا مسدودسازی، وضعیت
را تغییر دهید. برای تعویض کامپیوتر، دستگاه قبلی را از پنل لغو کنید تا نصب
جدید ظرفیت دستگاه را اشغال کند. دستگاهی که صریحاً لغو شده است تا رفع لغو
توسط مدیر دوباره وارد نمی‌شود؛ تغییر رمز هم اعتبار دستگاه‌های قبلی را رد
می‌کند و ورود مجدد لازم است.

حساب مشتری را staff یا superuser نکنید. مشتری فقط صفحهٔ حساب، اشتراک،
دستگاه‌های خودش و بکاپ‌های خودش را می‌بیند. رویدادهای تغییر اشتراک، ورود و
لغو دستگاه و عملیات بکاپ در پنل ثبت می‌شوند.

## ۴. آماده کردن برنامهٔ قابل تحویل

روی دستگاه ساخت ویندوز، فایل عمومی تولیدشده را کنار `buildwindows.bat`
بگذارید:

```text
FaceRecognition/subscription-client.json
```

وابستگی‌های `requirements.txt` شامل وابستگی‌های جدید اشتراک هستند؛ سپس
`buildwindows.bat` را اجرا کنید. فایل عمومی در پوشهٔ خروجی EXE کپی می‌شود.
**فقط فایل عمومی را منتقل کنید؛ `.env` و کلید خصوصی سرور هرگز به بستهٔ مشتری
نمی‌روند.** برنامهٔ فاقد تنظیم معتبر سرویس، محیط اصلی را باز نمی‌کند.

برای ساخت با GitHub Actions، دو repository variable عمومی تنظیم کنید:
`CLOUD_SERVICE_URL` و `CLOUD_PUBLIC_KEY`، مطابق همان فایل JSON. Workflow بدون
این تنظیمات، بستهٔ قابل فروش با سرور جعلی تولید نمی‌کند و متوقف می‌شود.

مدرسه هنگام شروع با ایمیل و رمز سایت وارد می‌شود. رمز محلی مدیر برنامهٔ
قدیمی هم برای حفظ حفاظت دیتابیس باقی مانده و با رمز سایت فرق دارد. پیش از
اتصال اولین دیتابیس، نام مدرسه نمایش داده و تأیید گرفته می‌شود. اتصال
دیتابیس یک مدرسه به حساب مدرسهٔ دیگر رد می‌شود.

تاریخ اعتبار و ظرفیت در صفحهٔ اشتراک و نوار پایین محیط اصلی دیده می‌شوند.
ذخیرهٔ توکن فقط در مخزن امن سیستم‌عامل انجام می‌شود؛ اگر Windows Credential
Manager یا مخزن امن Linux در دسترس نباشد، برنامه رمز/توکن را در فایل ساده
ذخیره نمی‌کند و ورود در اجرای بعد تکرار می‌شود.

## ۵. قطع دسترسی و اینترنت

- هر شروع برنامه به ارتباط آنلاین و پاسخ تازهٔ سرور نیاز دارد؛ فایل مجوز
  قدیمی اجازهٔ اجرای آفلاین پس از شروع مجدد نمی‌دهد.
- برنامهٔ در حال اجرا هر پنج دقیقه اعتبار را تازه می‌کند. خطای موقت شبکه
  تا پایان مجوز جاری تحمل می‌شود؛ تلاش مجدد محدود است.
- اعتبار هر مجوز حداکثر ۱۵ دقیقه و همیشه محدود به تاریخ پایان اشتراک است.
  با قطع اینترنت، پس از این مهلت محیط برنامه بسته می‌شود. این سیاست برای
  مدرسه‌ای با اینترنت نامطمئن باید پیش از فروش توضیح داده شود.
- پاسخ رد اشتراک/دستگاه دسترسی را در بررسی بعدی قطع می‌کند. قطع دسترسی در
  زمان آفلاین آنی نیست؛ حداکثر تا پایان اعتبار کوتاه جاری طول می‌کشد.
- ساعت یکنواخت اجرای جاری، nonce تازه و امضای Ed25519 جلوی تمدید با عقب
  بردن ساعت یا استفاده از پاسخ یک اجرای قبلی را می‌گیرند. ساعت سرور باید
  با NTP درست باشد.

با انقضا، دادهٔ مدرسه پاک نمی‌شود. دریافت بکاپ‌های قبلی از سایت برای حساب
فعال مدرسه حتی با اشتراک منقضی ممکن است. غیرفعال کردن کامل حساب کاربری
توسط مدیر، ورود و این دسترسی را هم مسدود می‌کند.

## ۶. بکاپ و بازیابی مدرسه

از منوی «اشتراک و پشتیبان»:

- «ساخت و ارسال بکاپ اکنون» یک snapshot سازگار با SQLite از دیتابیس زنده
  می‌گیرد؛ کپی سادهٔ فایل WAL در حال نوشتن نیست.
- ارسال خودکار روزانه فقط پس از انتخاب گزینهٔ رضایت مدرسه فعال می‌شود.
- بکاپ شامل اطلاعات دانش‌آموزان، حضور و غیاب، رویدادها، embeddings ثبت‌شده
  و تنظیمات داخل دیتابیس، از جمله رمز محلی هش‌شدهٔ مدیر است. توکن سایت، رمز
  سایت، مدل‌های برنامه، عکس‌های مرور رویداد و فایل‌های بیرون دیتابیس در آن
  نیستند. بکاپ فایل‌های خارج دیتابیس را جداگانه نگه دارید.
- فایل در HTTPS ارسال و روی سرور با AES-256-GCM و کلید مشتق‌شده برای همان
  مدرسه رمزگذاری می‌شود. این رمزگذاری سمت سرور است؛ اپراتور دارای کلید
  اصلی سرور توان رمزگشایی دارد و نباید آن را رمزگذاری سرتاسری نامید.
- اندازهٔ هر بکاپ حداکثر ۱۲۸ MiB است. پیش‌فرض هفت نسخهٔ اخیر نگهداری می‌شود؛
  نسخه‌های قدیمی پس از ثبت موفق فایل جدید حذف می‌شوند. فایل مشتری تا تأیید
  کامل رمزگشایی، tag و SHA-256 به گیرنده تحویل داده نمی‌شود.

برای بازیابی: برنامه را ببندید، دوباره وارد شوید و **پیش از ورود به محیط
دوربین** در صفحهٔ اشتراک، فهرست بکاپ‌ها را بگیرید و نسخه را انتخاب کنید.
دیتابیس پس از بررسی hash، ساختار، SQLite، ظرفیت و شناسهٔ مدرسه جایگزین
می‌شود. نسخهٔ قبل از بازیابی با نام `before-restore-*.sqlite3` در `data/`
نگه داشته می‌شود؛ این نسخه محلی و حساس است و باید امن نگهداری یا پس از
تأیید بازیابی پاک شود. هنگام اجرای دوربین، دکمهٔ بازیابی فعال نیست. قفل
فرایند جلوی اجرای دو نسخهٔ برنامه و بازیابی هم‌زمان را می‌گیرد.

پس از بازیابی، رمز محلی مدیر ممکن است رمز همان زمان بکاپ باشد و پیش از باز شدن محیط اصلی دوباره بررسی می‌شود. تغییر
دستگاه به انتقال توکن مخزن امن نیاز ندارد؛ روی دستگاه جدید وارد حساب سایت
شوید و ظرفیت دستگاه قبلی را از سایت آزاد کنید.

## ۷. بکاپ خودِ سرور و بازیابی VPS

بکاپ مدارس روی همان VPS، جایگزین بکاپ خود سرور نیست. روی یک دستگاه امن
جداگانه با `age-keygen -o recovery.key` یک هویت بازیابی بسازید و کلید خصوصی
آن را خارج از VPS نگه دارید. فقط گیرندهٔ عمومی `age1...` را به VPS بدهید:

```sh
sudo ./deploy/backup-server.sh age1YOUR_PUBLIC_RECIPIENT /secure/offsite/server-2026-10-23.age
```

`age` توسط helper اوبونتو نصب می‌شود. مسیر خروجی باید موجود و فضای آزاد
کافی باشد. سرویس وب هنگام snapshot سازگار، موقتاً متوقف و سپس دوباره شروع
می‌شود؛ دوربین‌های دارای مجوز معتبر تا مهلت خود ادامه می‌دهند. فایل شامل
PostgreSQL، blobهای رمزگذاری‌شده، `.env` و شناسهٔ commit است و با کلید عمومی
بازیابی رمزگذاری می‌شود. برای staging چند برابر حجم بکاپ فضای آزاد در نظر
بگیرید. فایل نهایی را واقعاً به فضای خارج از VPS کپی کنید و یک بار بازیابی
را آزمایش کنید. ارسال خودکار به ارائه‌دهندهٔ فضای بیرونی بدون حساب آن
ارائه‌دهنده پیکربندی نشده است.

بازیابی روی VPS **تازه و بدون دادهٔ تولیدی**:

۱. با کلید خصوصی روی دستگاه امن، بسته را باز کنید:

```sh
age -d -i recovery.key -o recovery.tar server-2026-10-23.age
mkdir -m 700 recovery
tar -xf recovery.tar -C recovery
```

۲. مخزن را در commit نوشته‌شده در `code-version.txt` دریافت و `server.env`
را با مجوز `600` در `deploy/.env` بگذارید؛ کلید جدید تولید نکنید.
۳. image را بسازید و فقط دیتابیس و Redis را شروع کنید:

```sh
sudo docker compose --env-file deploy/.env -f deploy/compose.yml build db web
sudo docker compose --env-file deploy/.env -f deploy/compose.yml up -d db redis
```

۴. پس از سالم شدن دیتابیس، داده را فقط در مقصد تازه بازیابی کنید:

```sh
sudo docker compose --env-file deploy/.env -f deploy/compose.yml exec -T db pg_restore -U face_service -d face_service --clean --if-exists --no-owner --exit-on-error < recovery/database.dump
sudo docker compose --env-file deploy/.env -f deploy/compose.yml run --rm --no-deps -T web tar -C /data/backups -xf - < recovery/blobs.tar
sudo docker compose --env-file deploy/.env -f deploy/compose.yml up -d
```

۵. DNS، HTTPS، ورود یک مدرسه و دریافت یک بکاپ را بررسی کنید. فایل‌های
رمزگشایی‌شدهٔ بازیابی، به‌خصوص `server.env`، محرمانه‌اند و پس از پایان کار
باید از محل staging حذف شوند.

## ۸. نگهداری و محدودهٔ تأیید

قبل از ارتقا، بکاپ سرور بگیرید؛ سپس کد را به نسخهٔ بازبینی‌شده ارتقا دهید و
`up -d --build` اجرا کنید. `.env` و کلیدها را حفظ کنید. لاگ‌ها:

```sh
sudo docker compose --env-file deploy/.env -f deploy/compose.yml logs --tail 100 web
sudo docker compose --env-file deploy/.env -f deploy/compose.yml exec web python -m service.manage check --deploy --fail-level WARNING
sudo docker compose --env-file deploy/.env -f deploy/compose.yml exec web python -m service.manage prune_backup_orphans
```

دستور آخر dry-run است؛ `--apply` فقط فایل‌های بدون رکورد و قدیمی‌تر از یک
روز را پاک می‌کند. این کار برای بقایای قطع برق/آپلود نیمه‌تمام است. فضای
دیسک، سلامت سرویس، تحویل ایمیل، تمدید گواهی و بکاپ خارج VPS را پایش کنید.
HSTS فقط برای همان hostname فعال است؛ دو توصیهٔ Django برای preload و اجبار
HTTPS همهٔ زیردامنه‌ها عمداً اعمال نشده‌اند تا دامنه‌های دیگر شما خراب نشوند.

هیچ نرم‌افزار دسکتاپی در برابر مالک کامپیوتر که کد اجرایی را تغییر دهد،
ضدکرک مطلق نیست. در این نسخه، تصمیم اشتراک سروری، توکن تصادفی قابل لغو،
کلید عمومی ثابت و مجوز کوتاه‌مدت استفاده شده است. این کنترل‌ها جای امضای
کد انتشار، امنیت VPS، نگهداری کلیدها یا ارزیابی امنیت مستقل را نمی‌گیرند.
تست خودکار، تضمین «صفر باگ امنیتی» یا تأیید عملکرد روی همهٔ دوربین‌ها نیست.
قبل از فروش، HTTPS واقعی، SMTP واقعی، بستهٔ EXE امضاشده و سناریوی دو دوربین
را روی نصب آزمایشی بررسی کنید. نتیجهٔ تست‌های انجام‌شده در
[یادداشت فنی](subscription-technical.md) ثبت می‌شود.
